# 订场保存、超时与重试（2026-11-02）

## 原问题

前端通用 API 在 12 秒后中止 fetch，直接把浏览器的英文中止错误显示为“保存失败”。服务端 POST/PATCH 在提交订场之后还串行等待 todo 同步、返场规则删除、组局结果核对和全量预估重训；保存后读取单场记录也通过全量历史 JOIN 再筛选。响应超时不能说明事务没有提交，旧 POST 重试可能追加一场相同账单。

## 修复

- 单场保存只读取该 session ID 的 JOIN 行，不再为了读回一场而遍历全部历史。
- 预估重训通过 Worker context.waitUntil 后台运行，保存成功不等待模型。模型端点原有的训练修订号检查仍可修复未完成的背景训练。前端保存成功后独立刷新预估，刷新失败不改成“保存失败”。
- todo、组局/返场规则和余额读取并行；可重试的辅助工作失败作为 followupWarnings，不否认已经确认的订场事务。PATCH 沿用原规则，不新增 todo 次数。
- 保存专用等待时间 60 秒；通用 API 的超时覆盖响应体读取，也与调用方 AbortSignal 合并，释放定时器和监听器。超时、取消、网络错误使用中文说明。
- 两个保存入口共用 sessionSaving 防重复提交和持久化请求编号。后台等待期间不乐观增加账目，只有服务器记录或有效回执确认后才显示成功。

## 一次性提交与恢复

0029_session_save_receipts.sql 只新增回执表和索引，不删改历史记录。request_id、规范化内容摘要、create/update 及实际 session_id 与账单和逐人快照在同一个 D1 批次中提交，EDC 原有 INSERT 触发器也包含在事务中。

同一请求编号只能重放相同规范化内容：响应丢失、并发或刷新重试返回同一已保存记录，不增加订场、出勤、训练修订号或 EDC 扣款。更晚的编辑不被旧请求覆盖。已删除的历史记录不能通过旧回执复活。不同请求编号仍可合法创建同一天的多场记录，不根据名字或金额自动合并。

session-save.js 将尚未确认的原请求保存在独立 localStorage 键 badminton-session-save-pending-v1 中。请求超时或结果不完整时，先用管理版 GET /api/session-save-receipts/:requestId 核对；仍未知则保留原请求并明确提示保持原内容重试。此查询没有新增订场或扣款。浏览器存储不可用时不提交无法安全恢复的写入。

如果尚未确认时修改表单，先安全重试原请求；原记录确认后，当前修改不会作为新的 POST 偷偷插入，而是提示“上次已保存，当前修改尚未提交”，将下一步切为编辑已保存的记录。成功后清理待确认意图，下一场即使内容相同也生成新编号。

GitHub 继续只读；保存、回执查询以及人员变更在管理版进行。

## 验证

npm run test:session-save 覆盖真实迁移 SQLite、原子回执、EDC exactly-once、事务回滚、并发及丢响应重放、新旧更新隔离、删除保护、单场 SQL、后台模型不阻塞、辅助工作失败、持久化恢复、改表单隔离、防重复提交、存储故障，以及请求头/响应体/外部信号超时。

浏览器使用隔离本地 D1，模拟超过 12 秒的回复、保存成功但丢响应、请求未提交及刷新重试、表单修改和只读保护。生产库仅进行读取、备份和新增空回执表，绝不写入测试订场或删除疑似重复历史。
